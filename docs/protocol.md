Scratch担当向けの共有仕様です。バックエンド（Python/scratchattach）とScratchプロジェクトは
**TurboWarpのクラウド変数**でやり取りします。

## 前提

- プロジェクトは **TurboWarp** で実行する
  - 観客・出演者はScratchアカウント不要（本家scratch.mit.eduのクラウド変数はログイン必須のため使わない）
- クラウド変数に入れられるのは**数値のみ**
- TurboWarpのクラウド変数は**全員が切断すると値が消える**
  - Python側に `resync`（全状態の再送）機能があり、Scratch側をリロードしたら司会者画面の「困ったとき」→「Scratch に今の状態を送り直す」で今の状態を送り直せる（CLIの `resync` と同じ）
  - 作り直したステージ画面は、途中の段階（例: チームの3問目の正解発表）をいきなり受けても、そのときの値だけから画面を組み立てる。再読み込みするだけで今の画面に戻り、「送り直す」を押せば開いたままでも組み立て直す。元のプロジェクトを TurboWarp で直接開いた場合は、途中で開き直すと崩れる（[#52](https://github.com/suzuka-kosen-festa/2026-suzuleague/issues/52)）
  - **Python側は、ステートを1秒以上あけて1つずつ送ります**（前の「次へ」から1秒たたない「次へ」は取り消す）。2つのステートがほぼ同時に届くと、Scratch側は `P2S_SEQ` の変化を1回しか検知できず、間のステート（正解発表など）を処理できないため（2026-10-12 に実機で発生）
- ルームID: 開発中は `suzuleague-dev`、**本番は `1364239598`**
  （Scratch担当のプロジェクト <https://scratch.mit.edu/projects/1364239598/> のID。
  Python側は環境変数 `SUZULEAGUE_PROJECT_ID` で切替可能）

### ⚠ 元のプロジェクトを直接開くときは、URLに `?cloud_host=` を必ず付ける

本番では TurboWarp の公開サーバではなく、**このイベント専用に立てたサーバ**を使う。
Render から配るステージ画面（`/stage/view/`・`/stage/play/`）は、配っているサーバにそのままつなぐので何も付けなくてよい。
Scratch担当が手元で試すときなど、元のプロジェクトを TurboWarp で開く場合のURLは次の形になる。

```
https://turbowarp.org/<プロジェクトID>?cloud_host=wss://suzuleague-cloud.onrender.com
```

**これを付け忘れると、何のエラーも出ないまま通信できない。** Scratch側は公開サーバ、
Python側は専用サーバという別々の部屋に入ってしまい、互いの変数が見えなくなる。
画面上は普通に動いているように見えるので、原因に気づくまで時間を溶かす。

専用サーバに切り替えた理由は、公開サーバに**1部屋128人の上限**があり、
観客のスマホ参加分を足すと足りないため（[詳細](./architecture.md#同時接続数の上限とセルフホスト方針)）。

## 変数一覧

### Python → Scratch（Scratch側は読むだけ。書き込まないこと）

| クラウド変数 | 内容 |
|---|---|
| `☁ P2S_SEQ` | 更新カウンタ。**Scratchはこの変数の変化だけを監視**し、変化したら他の変数を読む |
| `☁ P2S_STATE` | 進行ステート（下表） |
| `☁ P2S_TEAM` | 現在のチーム番号 (1〜4、開始前は0) |
| `☁ P2S_ROUND` | 現在のラウンド (1〜5、開始前は0) |
| `☁ P2S_QID` | 問題ID（1〜20。チーム1が1〜5、チーム2が6〜10…）。観客ページはこの番号で問題文を出す |
| `☁ P2S_CORRECT` | 正解パーセント。**非公開のあいだは -1**（正解発表・ラウンド結果・チーム結果のときだけ実際の値になる） |
| `☁ P2S_BALLOONS` | 現在チームのバルーン残数 |
| `☁ P2S_ANSWER` | 出演者の回答パーセント。**届いていないあいだは -1**（出題のたびに -1 に戻る）。回答が届いた時点でこの変数だけが変わり、`P2S_SEQ` は変わらない |
| `☁ P2S_SCORES` | 全チームの残りバルーン。`1` のあとにチーム番号順で3桁ずつ並べた数（5問を終えていないチームは `999`）。例: チーム1が38・チーム2が0・残りはまだ → `1038000999999` |
| `☁ HEARTBEAT` | Python生存確認。約15秒ごとに更新される（接続中インジケータなどに利用可） |

> 送信順序について: 1回の状態更新では `P2S_SEQ` が**最後に**送信されます。
> そのため「SEQが変わった時点で他の変数は更新済み」と考えてOKです。

> **値は文字列で届きます**（`"3"`。2026-10-13〜）。数値で送っていたときは、Scratch の
> 「コスチュームを（`☁ P2S_ROUND`）にする」がコスチュームの名前ではなく番号で選ばれ、
> 問題番号の表示が1つ前にずれていた。Scratch のエディタで変数に値を入れて試したときと同じ動きになる。

`☁ P2S_ANSWER` は、出演者がどこから答えても同じ値が入る（Scratch のテンキー・司会の代理入力・予備の回答画面）。
入力なしの大画面用の画面は、この変数を見て出演者の予想を出す。出演者用の画面も、正解発表のときはこの値を
予想として使うので、採点された回答と画面の演出が食い違わない。

### Scratch → Python（Python側は読むだけ）

| クラウド変数 | 内容 |
|---|---|
| `☁ S2P_SEQ` | Scratch側の送信カウンタ（回答送信のたびに+1） |
| `☁ S2P_ANSWER` | 回答されたパーセント (0〜100の整数) |
| `☁ S2P_ACK` | 演出完了などの通知。`1` = バルーン割れアニメーション完了。裏方PCはログに出すだけで、作り直したステージ画面は送らない |

回答送信時は `S2P_ANSWER` → `S2P_SEQ` の順に書き込んでください。

## 進行ステート (`☁ P2S_STATE`)

| 値 | ステート | Scratch側の表示イメージ |
|---|---|---|
| 0 | 待機 | タイトル画面 |
| 1 | チーム紹介 | チーム名・登場演出 |
| 2 | 出題 | 問題文表示（`P2S_QID` の問題） |
| 3 | 回答受付 | シンキングタイム演出・回答入力UI |
| 4 | 正解発表 | `P2S_CORRECT` を表示、バルーン割れアニメーション |
| 5 | ラウンド結果 | バルーン残数表示 |
| 6 | チーム結果 | クリア（`P2S_BALLOONS` > 0）/ ゲームオーバー演出 |
| 7 | 回答受付（エキシビション） | 3と同じだが**採点なし**であることを表示 |
| 8 | 全体結果 | 表彰式画面 |

- ステート遷移はすべて裏方PC（Python）が進めます。操作するのは司会者画面の「次へ」（またはCLIの `next`）です
- ゲームオーバー（バルーン0）になったチームの残り問題は、自動的にステート7（エキシビション）で出題されます

## 観客用クライアント

観客がスマホから参加する画面（`https://suzuleague-cloud.onrender.com/suzuleague.html`）も、
**ステージ画面とまったく同じ変数を受け取る**。
クラウド変数は同じ部屋の全クライアントへのブロードキャストなので、
裏方PCが状態を書き換えれば**ステージも観客も同じタイミングで次の問題に進む**。
同期のための追加の仕組みは要らない。

満たすべき条件は3つだけ。

1. ステージ画面と**同じ room ID** に繋ぐ
2. ステージ画面と**同じ cloud サーバ**に繋ぐ（`?cloud_host=wss://suzuleague-cloud.onrender.com`）
3. ステージ画面と同じく `☁ P2S_SEQ` の変化を検知して他の変数を読み直す

実測では150クライアントに配信しても端末間の差は数ミリ秒だった
（[architecture.md の進行の同期](./architecture.md#進行の同期)）。

### 正解だけは、Scratch の演出が終わるまで出さない

Scratch 画面は正解発表（ステート4）を受けてからゲージを動かし、**13.3〜13.7秒後**に正解を出す（2026-10-13 に実測）。
観客ページが受け取ってすぐ正解を出すと、大画面より先に答えが分かってしまう。
そこで観客ページは、ステート4を受けてから**15秒**は「正解は…？」のまま待つ（`audience_template.html` の `REVEAL_DELAY_MS`）。

- 司会がラウンド結果（ステート5）へ進めたら、待たずに出す
- 待っているあいだに再読み込みしても、待ち直しにはならない（出してよい時刻を端末に覚えている）
- 成績（誤差）は待たずに数えて送る。画面には出ないので先に分かることはない
- Scratch 側でゲージの長さ（スプライト「正解」の「判定までの時間」）を変えたら、この秒数も合わせる

### 観客側は S2P_* に書き込まない

**観客用の画面は `P2S_*` を読むだけ**で、送信するのは接続時の handshake のみ。
`☁ S2P_ANSWER` は挑戦者の回答を入れる場所なので、観客が書き込むと
**挑戦者の回答として採点されてしまう**。

観客の回答は**その端末の中で採点**する（正解発表時に届く `P2S_CORRECT` と
自分の回答の差でバルーンを減らす）。観客ランキングのための成績（誤差の合計）は、
クラウド変数ではなく HTTPS API（`/api/score`）で送る（[後述](#https-apiスマホの画面と裏方pc)）。

### 途中から参加した観客

cloud サーバは新規接続時に現在の変数値をまとめて送るため、
イベントの途中でQRコードを読んだ観客も、接続した瞬間に現在の問題から参加できる。

## ステージ画面は元のプロジェクトから作り直して配る

Scratch担当のプロジェクト（絵・音・演出）を元に、`uv run python -m suzuleague.stage` で2つの画面を作って Render から配る
（手順は [development.md](./development.md#ステージ画面を作り直す)）。

| 画面 | URL | 元のプロジェクトとの違い |
|---|---|---|
| 大画面用 | `https://suzuleague-cloud.onrender.com/stage/view/` | テンキー・GO・Delete がない。出演者の予想は `☁ P2S_ANSWER` から出す。`S2P_*` には書き込めない |
| 出演者用 | `https://suzuleague-cloud.onrender.com/stage/play/` | テンキーで答える。GO を押すと `☁ S2P_ANSWER` → `☁ S2P_SEQ` の順に書く（元と同じ） |

入れ替えるのは、裏方PCとやり取りするスプライト「通信」のスクリプトだけ。入れ替え後は次のように動く。

- **1つ前の段階から順に進んだとき**は、元と同じメッセージを送って演出を流す
- **それ以外**（開いた直後・同じ状態を送り直された・段階を飛ばした・チームが替わった）は、`初期化` で画面を消し、そのときの値から組み立て直す

そのため、どの段階で再読み込みしても今の画面に戻る。緑の旗の押し直しも「送り直す」も要らない。
組み立て直した画面に出ないのは、その場かぎりの飾りだけ（ゲームオーバーになった問題の「GAME OVER」の文字と、クリアした問題の「CLEARED」の文字）。
問題文・予想・正解・残りバルーン・背景は元どおりに出て、次の問題からは通しで見たときと同じになる。

### 元のプロジェクトに頼っていること（Scratch担当へ）

演出のスクリプトには手を入れず、**次のメッセージと変数の名前・意味**だけを頼りにしている。
ここを変えるときは、変える前に知らせてほしい（作り直しのコマンドが「作りが変わっています」と止まる）。
絵・音・演出の中身は自由に直してよく、直したら作り直せば取り込める。

| 種類 | 名前 |
|---|---|
| 進行のメッセージ | `初期化`・`1_チーム紹介`・`演出_風船登場開始`・`進行_次の問題へ`・`4_正解発表`・`5_ラウンド結果表示`・`6_チーム結果`・`7_エキシビジョン回答受付`・`演出_バルーン破裂完了`・`回答_確定` |
| 組み立て直し用のメッセージ | `途中復帰_背景同期`・`途中復帰_出題UI同期`・`途中復帰_入力監視開始` |
| 変数 | `回答中`・`風船の数`・`予想%`・`正解%`・`誤差`・`エキシビション`・`途中復帰`・`復帰描画中` |
| リスト | `★入力した文字`・`得点表` |
| スプライト | `通信`（中身は入れ替える）・`問題`・`キー`・`決定`・`delete` |

### 全体結果の画面は、こちらで作ったものに置き換えている

元の得点表（`8_終了`）は、チーム5つぶんの空のマスの上に Scratch のリスト表示が重なるだけだったので使っていない。
代わりに、作り直しのときにスプライト「結果発表」を足している（`stage_result.py`。絵も SVG でそこから作る）。

- 「通信」が `☁ P2S_SCORES` からリスト `得点表` にチーム番号順で残りバルーンを入れ、`結果_出す` を送る
- 「結果発表」が、チームごとのカード（残りバルーン・順位）を1枚ずつ出し、最後に優勝チームへ金の枠と「優勝」の札を付ける。残り0のチームは順位の代わりに「GAME OVER」
- チームの数はリストの長さで決まる（本番は4、デモは1。5チームまで入る）
- 優勝は裏方PCと同じ決め方（残りバルーンが最多。同数なら先のチーム。全チームが0なら優勝なし）
- ステージ画面はチーム名を知らないので、カードには「チーム1」のように番号で出す（チーム名は観客ページと司会者画面に出る）

「通信」と「結果発表」のほかに足しているのは次の6つで、どれも元のスクリプトは消していない。

- 各チームの1問目で、登場の効果音のあとに `回答中` を `0.1` に戻すのを「まだ `0` のときだけ」にした（効果音の途中で回答受付へ進めてもテンキーが出る。[#53](https://github.com/suzuka-kosen-festa/2026-suzuleague/issues/53)）
- スプライト「問題」が `途中復帰_出題UI同期` を受けたら、コスチュームを「チーム番号-何問目」に切り替える
- 組み立て直しの前に、動いている途中の演出（ゲージ・風船の数え下げ・音楽の繰り返し）を止める
- `初期化` を受けたら GAME OVER の文字を消す
- 組み立て直すとき、数字のクローンを「残り」の風船の位置で作る（残り0の「0」は、クローンができた場所にそのまま出るため）
- ゲームオーバーになったチームを組み立て直すとき、「残り」の風船を正解発表のあいだだけ出す（元はゲームオーバーの演出の中で始めている）

## HTTPS API（スマホの画面と裏方PC）

クラウド変数は誰でも書き込めて、値が全員に流れる。そのため「特定の人だけが送るもの」は
cloud サーバ（Render）の HTTPS API で受け付ける。実装は
[inouekoshi/cloud-server](https://github.com/inouekoshi/cloud-server) の `src/hostApi.js`・`src/rankingApi.js`。

| メソッド・パス | 誰が | 認証 | 内容 |
|---|---|---|---|
| `POST /api/host/command` | 司会者画面 | `X-Host-Token` | 操作を預ける。`{"type":"next","expect_state":2}` / `{"type":"answer","value":45}` |
| `GET /api/host/command?after=N` | 裏方PC | `X-Host-Token` | 預かった操作のうち `seq > N` のもの。`{"latest":N,"commands":[...]}` |
| `POST /api/host/state` | 裏方PC | `X-Host-Token` | 進行の状態を預ける（`host.py` の `build_host_state`） |
| `GET /api/host/state` | 司会者画面 | `X-Host-Token` | 状態と、裏方PCから最後に届いてからの秒数（`age`） |
| `GET /api/host/ranking` ・ `POST /api/host/ranking/hide` ・ `POST /api/host/ranking/reset` | 司会者画面 | `X-Host-Token` | 観客ランキングの一覧・名前の非表示・リセット |
| `POST /api/player/answer` | 出演者の回答画面 | 4桁の合言葉（本文の `code`） | `{"code":"4821","value":45,"question_id":7}`。回答受付中・同じ問題のときだけ受け付ける |
| `GET /api/player/state` | 回答画面・観客ページ | なし | 公開用の状態。**正解は発表後にしか含まない** |
| `POST /api/score` | 観客ページ | なし | `{"id","name","error_sum","answered","last_question"}` |
| `GET /api/ranking?id=&limit=` | 観客ページ・回答画面 | なし | 上位と参加人数、自分の順位 |

- `X-Host-Token` は Render の環境変数 `HOST_TOKEN` と裏方PCの `SUZULEAGUE_HOST_TOKEN` に同じ値を入れる。未設定ならAPIは503
- 出演者の合言葉は裏方PCがチームごとに発行し、`/api/host/state` の `player_code` で司会者画面に出す。
  間違いが1分に30回続くと30秒間すべて受け付けない
- 出演者の回答も、司会の「次へ」と同じ郵便受け（`/api/host/command` の取り出し）で裏方PCに届く。
  裏方PCは合言葉と問題番号をもう一度確かめてから回答として受け付ける

本番の出演者はステージ画面（出演者用）から `☁ S2P_ANSWER` で回答する。回答画面（`/api/player/answer`）は予備で、どちらから来ても同じ扱いになる。

## 問題文の扱い（番号で参照する）

クラウド変数は数値しか送れないので、問題文そのものは送らない。それぞれの画面が問題文を持ち、届いた番号で選ぶ。

- **観客ページ**: 書き出すときに20問の問題文を埋め込み、`☁ P2S_QID` で選ぶ
- **ステージ画面**: 問題文を画像（スプライト「問題」のコスチューム）で持ち、`☁ P2S_TEAM` と `☁ P2S_ROUND` から「2-3」のような名前を作って切り替える。チームと問題の順番が決まっているので、`P2S_QID` と同じ問題になる

問題を差し替えたら、`questions.py`・ステージ画面の画像・観客ページの3か所をそろえる（Scratch担当に渡す文言は
[scratch/README.md](./scratch/README.md#問題を差し替えるとき)）。

## 動作確認の方法

ステージ画面なしでも、Python側だけで両側を動かして試せる。

```
# ターミナル1: 司会ダッシュボード
```

## 技術的な注意（ハマりどころ）

- **1回のクラウド変数書き込みは1変数ずつ**行うこと。
  （参考: Python側ライブラリの一括送信機能はTurboWarpサーバに無視される不具合があり、
  1変数ずつ送る実装にしてある）
- `☁ P2S_CORRECT` は正解発表前は `-1`。Scratchの見た目に出さないよう注意
- **`☁ P2S_*` には書き込まないこと。** 同じルームに大画面・出演者の端末・観客のスマホがいるので、全員の画面が狂う
- **正解の数字はScratch側に持たせないこと。** Scratchプロジェクトは中身を誰でも
  見られるので、正解を埋め込むと当日ネタバレしうる。正解はPython側から
  発表のタイミングで `P2S_CORRECT` として届く
- 公開サーバ（`?cloud_host=` なし）には同一IPからの接続頻度制限があり、
  短時間に大量のリロードを繰り返すと一時的に接続できなくなる。
  **専用サーバにはこの制限はない**（cloud-server本体に実装がないことをソースで確認済み）

## 繋いだときに出やすい不具合

Python側とScratch側を初めて繋ぐときは、**エラーが出ないまま動かない**種類の
不具合が起きやすい。詰まったら次を疑ってほしい。

| 症状 | 疑うところ |
|---|---|
| 変数がまったく届かない | `?cloud_host=` の付け忘れ（上記）。room ID の食い違い |
| 一部の変数だけ届かない | **変数名の綴り・大文字小文字**。クラウド変数は名前が違うと黙って無視される |
| たまに表示が飛ぶ | `P2S_SEQ` の変化を見ずに個別の変数を監視していないか |
| 回答がPython側に届かない | `S2P_ANSWER` → `S2P_SEQ` の**順序**。SEQを先に書くと取りこぼす |
| 数値がおかしい | Scratch側から文字列として送られていないか |

裏方PCのダッシュボードには受信した回答が表示されるので、
**どちらまで届いているかは裏方PCの画面で切り分けられる**。
